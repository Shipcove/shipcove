Sécurité

Principe : le code exécuté par l’agent n’est pas de confiance. La sandbox ne détient aucun secret permanent et ne peut rien publier sans approbation humaine.

Sandboxes

  • Utilisateur non privilégié, cap-drop ALL, no-new-privileges, limites de CPU, mémoire, processus et disque.
  • Réseau interne sans route vers Internet ni vers le backend (PostgreSQL, Vault, S3…).
  • Sortie uniquement via le proxy de la gateway, avec une liste blanche de domaines (registres de paquets…). Les forges Git y sont refusées : git push, gh, glab ne fonctionnent pas.
  • Services d’appui : mêmes durcissements, aucun accès réseau supplémentaire.

Jetons et secrets

  • La sandbox reçoit un jeton de run à durée limitée, utilisable seulement auprès de la gateway (LLM, lecture Git, outils de la plateforme).
  • Clés de modèles, jetons Git, secrets SSO et MCP sont dans Vault ; l’API ne les renvoie jamais.
  • Les secrets de projet sont masqués dans les sorties, le flux temps réel, la base et retirés des requêtes vers le fournisseur LLM.
  • Chaque service a sa propre identité Vault et une politique limitée à ses chemins.

Git

Publication par le broker, après approbation de l’opération exacte (commit figé, branche, cible) ; une approbation est à usage unique et invalidée si la branche a bougé. Un jeton n’est présenté qu’à l’hôte de sa connexion ; HTTPS est obligatoire sauf exception explicite de l’administrateur.

Comptes et navigateur

  • Mots de passe Argon2id, MFA TOTP (obligatoire pour les administrateurs), verrouillage et limitation de débit.
  • Sessions côté serveur, cookies HttpOnly / SameSite, protection CSRF par double soumission.
  • CSP stricte sans script inline, en-têtes de sécurité, previews sur un domaine distinct avec jeton.
  • SSO : PKCE, état à usage unique, assertions SAML signées ; jamais de fusion de comptes par email.

Fichiers

Pièces jointes et archives contrôlées (type réel, taille décompressée, nombre d’entrées, chemins), analyse antivirus par ClamAV si CLAMAV_HOST est configuré, bloquante en cas d’indisponibilité, exécutables refusés.

Confidentialité

Une conversation n’est lisible que par son propriétaire et les personnes avec qui il l’a partagée nommément — les administrateurs plateforme compris. Les actions d’administration sont auditées ; la rétention est configurable avec gel légal.

Points d’attention en production

  • Socket Docker : le worker y a accès, ce qui équivaut à un accès root à l’hôte. Dédiez l’hôte à la plateforme ; à terme proxy de socket, gVisor ou provider Kubernetes.
  • Déverrouillage de Vault : les clés sont sur disque (.secrets/). Protégez-les ou utilisez un auto-unseal KMS.
  • TLS : terminé par votre reverse proxy ; le trafic interne Compose n’est pas chiffré.
  • Secrets de projet : utilisables par l’agent de tout membre du projet ; réservez-y des identifiants de développement.

Pour signaler une vulnérabilité, ouvrez un avis de sécurité privé sur le dépôt GitHub plutôt qu’un ticket public.
