Environnement et services

Ce dont l’agent a besoin pour installer, lancer et tester le code : script de démarrage des sandboxes, image et services d’appui.

Script de démarrage

Un script unique, défini par l’administrateur dans Administration → Sandboxes & previews → Script de démarrage, commun à toutes les sandboxes (avec ou sans dépôt). C’est l’endroit pour configurer les registres et miroirs de l’entreprise et installer des outils communs :

npm config set registry https://npm.example.corp/
pip config set global.index-url https://pypi.example.corp/simple
npm install -g pnpm@10
  • Exécuté en bash dans /workspace, sans droits root, dans chaque nouvelle sandbox avant le premier message traité par Pi, et à nouveau quand il change : il doit être idempotent.
  • Ce qu’il produit dans /workspace est conservé (checkpoint) ; le reste (~/.npmrc, configuration pip, outils globaux dans ~/.local) vit avec la sandbox et est refait à la suivante.
  • Sa sortie apparaît dans la conversation ; en cas d’échec, l’agent est informé et le run continue. Durée maximale : 20 minutes par défaut.
  • Les hôtes contactés doivent figurer dans le réseau sortant autorisé (même page).
  • uv ne lit pas la configuration de pip : pour un index privé, écrivez aussi ~/.config/uv/uv.toml ([[index]] avec default = true).

Le script est stocké en clair et s’exécute dans la sandbox, où l’agent peut lire les fichiers qu’il écrit : n’y mettez que des identifiants en lecture seule, à portée minimale.

Image de sandbox

Toutes les sandboxes utilisent l’image par défaut déclarée par l’administrateur. L’image officielle ghcr.io/shipcove/shipcove-sandbox contient Pi (et ses plugins : questions, captures d’écran, plan), Git, Python, uv, Node.js, npm, Playwright et Chromium ; une image dérivée part de celle-ci (FROM ghcr.io/shipcove/shipcove-sandbox:<version>@sha256:…), par exemple pour ajouter un JDK, Go ou Rust. Changer l’image par défaut recrée les sandboxes au run suivant.

Services lancés par l’agent

Pi démarre lui-même, quand il en a besoin, des bases de données, caches ou files de messages choisis dans un catalogue géré par l’administrateur (Administration → Sandboxes & previews) : image, port, sonde de santé, variables par défaut, mémoire. Rien ne démarre tant que l’agent ne le demande pas ; aucun réglage côté utilisateur.

  • L’agent utilise l’outil platform_services : start, stop, status, logs, catalog.
  • Chaque service partage le réseau de sa sandbox : joignable sur localhost depuis celle-ci uniquement, sans plus d’accès sortant qu’elle. Conteneurs durcis et limités (mémoire, CPU, processus), 4 services au plus par sandbox par défaut.
  • Les services durent autant que la sandbox et disparaissent avec elle : données éphémères, l’agent refait migrations et données de test après un redémarrage.

Miroir de registre

Sans accès direct aux registres publics, Administration → Sandboxes & previews → Miroir de registre fait télécharger les images des services depuis votre miroir (Harbor, Nexus, Artifactory…) : chaque registre d’origine est associé à un préfixe du miroir (docker.io → harbor.corp/dockerhub donne harbor.corp/dockerhub/library/redis:7.4-alpine), avec des identifiants facultatifs stockés dans Vault et un repli possible sur le registre d’origine. Le téléchargement est fait par le moteur Docker de l’hôte : un miroir en HTTP ou à certificat interne doit y être déclaré.

Les services d’appui sont disponibles avec le provider Docker ; ils le seront sur Kubernetes (conteneurs annexes du Pod) avec la validation du chart Helm.
