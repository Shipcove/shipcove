User guide

Everything you need to hand tasks to Pi and stay in control of the result.

Conversations

Everything starts with a conversation. The home page is a new conversation: write your request and send it. Each conversation has its own files, sandbox and history; code is shared between conversations through Git.

  • Optional Git repository: under the input box, No repository opens the list of repositories available through your Git connections (with search). The repository is cloned on its default branch, through the platform gateway: no token ever enters the sandbox. Without a repository, Pi gets an empty sandbox.
  • Automatic title: generated from the first message (by the model chosen by the administrator, otherwise the start of the message). Rename it from the header (pencil icon or double-click): your title is never replaced again.
  • Sidebar: conversations are grouped by Git repository (collapsible groups, + to start a conversation in that repository), then those without a repository, sorted by date (today, yesterday, last 7 and 30 days, older).
  • The sandbox starts at the first message and stops after a period of inactivity (15 minutes by default). Its files and Pi’s state are restored at the next message.
  • Header: on the right, Share, then three panes — the file explorer, the panel (Git and Previews tabs) and Pi’s plan — only one of which is open at a time, then conversation deletion.
  • A conversation can be put to sleep from its header, and deleted from its header or from the trash icon shown on hover in the sidebar. Deletion is permanent: a running task is interrupted and the queue cancelled, then the sandbox and its services, the backups (checkpoints and Pi’s state), the files, attachments, screenshots and the whole history are erased. Only the consumption remains counted in your quota.

The conversation

Sending a request

Write your request and press Enter (Shift+Enter for a new line). Pi’s answer is streamed; every tool call (command, read, write…) appears in a collapsible card with its output, duration and the files it touched.

While Pi is working

  • Queue: a message sent during a generation is queued and shown above the input box; it is processed automatically when the current task ends.
  • Interrupt: the square button, or Esc twice in a row, stops Pi cleanly; what was written is kept.
  • Duration: the time elapsed since the start of the task is shown next to “Pi is working…”.
  • Scrolling: the conversation follows Pi’s work as long as you are at the bottom. Scroll up to read back: it no longer pulls you down, and a ↓ button above the input box takes you back. Sending a message always brings you back to the bottom.
  • Steps: consecutive reasoning and commands are grouped into a collapsible block; a failed command is marked by a red cross on its card.

Following and controlling changes

“Git” tab

The side panel shows the working branch and lets you switch it (local branches, or remote ones: the local branch is then created). The selector follows the branch switches made by Pi; a switch of yours is noted in the conversation and reported to Pi at its next turn. It is unavailable while Pi is working, and Git refuses the switch if your uncommitted changes conflict.

Below, the git diff against the last commit: added, modified or deleted files with their line counts; click a file to see its differences (unified or side by side). Everything else — commits, push, pull requests — happens in the conversation with Pi. Every commit made in the sandbox carries the Co-Authored-By: Shipcove trailer (address set by the administrator).

File explorer

The file icon opens the explorer (search, tree, tabs). Manual editing is disabled by default; if the administrator enables it, a save is refused when Pi has changed the file in the meantime (no silent overwrite).

Going back

When you hover one of your messages, Go back before this message restores the conversation’s files to their state before that run. The conversation is kept, Pi is told at the next message, and the “Files restored…” message offers Undo. Unavailable while Pi is working.

Skills

A skill is a folder of instructions for Pi, in markdown only: a SKILL.md file (with a name and description header) and, if needed, other .md files organized in folders and subfolders (references, procedures, examples). No scripts or binaries. Pi sees the description of enabled skills and loads their content when the task calls for it; type / in the input box to force one or more.

  • Skills & MCP: everyone turns each skill on or off for themselves with its switch, at any time. Enabled skills are highlighted (green check), with their count, Enabled / Disabled filters and grouping by category (defined by administrators; each author files their skills under one of them). A skill is available as soon as it is created.
  • Import .zip: an archive with SKILL.md at the root (or in a single root folder); the name and description are read from the header. Only markdown files are kept: the others (scripts, images…) are ignored and listed.
  • Editor: tree (new file or folder, upload of .md files into the selected folder, rename or move, delete), editing with preview (code, preview or both side by side; links to other files of the skill open them), choice of category. Saving replaces the content; the skill can also be deleted. Export downloads the skill as a .zip.
  • Limits: 300 files, 1 MB per file, 5 MB in total. Archives containing dangerous paths (.., absolute paths) or symbolic links are refused.

Attachments

Drag and drop, paste or add files (20 MB and 10 files per message by default). Images are passed to the model if it accepts them; other files are placed in the sandbox (/workspace/.cap/attachments/…, outside Git). Executables, dangerous archives or archives too large once decompressed, and inconsistent types are refused.

Services, environment and dependencies

Pi starts by itself, when it needs them, the services approved by the administrator (PostgreSQL, Redis, RabbitMQ…), reachable on localhost in the sandbox. The sandbox startup script (registries, mirrors, tools) is defined by the platform administrator: see Environment and services.

Git: publishing the work

  1. Connect your account: Settings → Git connections → Connect via … (OAuth, forges configured by the administrator).
  2. Pi then works autonomously with git, gh and glab, on your behalf: it pushes its branches, opens pull / merge requests, follows the CI, reads the logs and answers reviews.
  3. For the default branch or a protected branch, a merge or a branch deletion, it creates an approval request, shown in the conversation under its message: check the exact operation (commits, diff), then Approve or Reject. An approval can be used only once; if the branch has changed since, a new request is needed.

Your GitHub / GitLab token never enters the sandbox: the platform adds it on the way. Repository settings, access rights and long-lived keys or tokens stay out of the agent’s reach. Every write by Pi on a forge is logged.

Pi’s plan

For a complex task (three steps or more, several files to change), Pi sets out a plan: the list of its steps, kept up to date while it works. The Plan button in the header opens this plan next to the conversation: the current task is highlighted (and a dot appears on the button), completed tasks are checked and struck through, a counter shows the progress. For a simple request, Pi does not make one. Not to be confused with Plan mode, where Pi prepares a plan without changing anything.

Pi’s questions

When a decision is yours to make (scope, technical choices, trade-offs), Pi asks its questions as a form in the conversation: single or multiple choice, recommended option highlighted, free “Other” answer. Submit these choices sends your answers and Pi resumes. It stops while waiting: the sandbox can go to sleep, nothing expires. Questions are also possible in Plan mode.

Screenshots

As soon as Pi creates or changes a web interface, it starts the project in the sandbox and takes screenshots with the sandbox’s Chromium (desktop, mobile, dark theme, after a click or some input), without you asking. They appear as thumbnails in the thread, always visible, even when Pi’s steps are collapsed; click to enlarge them (arrows to move between them, Esc to close). If the model accepts images, Pi reviews its screenshots itself to fix the rendering. People the conversation is shared with see them too.

Downloadable files

When Pi produces a deliverable — a README, a report, a CSV export, an image, an archive… — it offers it as a download: a card per file appears in the conversation (name, type, size); click to download it. The file is copied when Pi shares it: if it changes it later, it shares it again. You can also simply ask “give me file X”. People the conversation is shared with can download these files too.

Previews

When Pi starts a server (port 3000, 5173…), open it from the Previews tab of the panel: it is served on a separate domain, protected by a token. Three ports per conversation by default.

Sharing

The share button gives read-only access to the conversation and its files to named users of the platform (search by name or username); it can be revoked at any time. Nobody else — administrators included — can read a private conversation.

Quotas

Consumption is limited over two rolling windows, 5 hours and 7 days, on your personal quota: a single counter per person, for all your conversations, that nobody else consumes. The Usage page and the ring of the input box show it as a percentage. At 100%, Pi is paused cleanly and resumes as soon as the quota allows (Resume button).

Notifications and account security

  • Notifications: task completed or failed, approval required, quota reached… in the application and, depending on your preferences, by email.
  • Settings → Security: password, two-factor authentication, active sessions (revocable), linked sign-in identities (SSO).
