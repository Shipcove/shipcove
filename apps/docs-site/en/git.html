Git forges

Users connect their GitHub / GitLab accounts with OAuth, through the forges declared by the administrator. Pi then uses git, gh and glab autonomously; tokens stay in Vault and never enter the sandboxes.

Declaring a forge

Administration → Git forges, one OAuth application per forge:

ForgeWhere to create the application
GitHub.comSettings → Developer settings → OAuth Apps → New OAuth App
GitHub Enterprise ServerSame path, on your instance
GitLab.comPreferences → Applications (confidential application)
Self-hosted GitLabAdmin Area → Applications → New application (confidential)

  1. Add

    Type, display name, host (fixed for SaaS offerings), client ID, client secret (Vault).

  2. Declare it on the forge

    The callback URL shown by the console (https://<your-domain>/api/v1/me/git-connections/oauth/<id>/callback) and the scopes: GitHub repo read:user user:email read:org, GitLab api read_user read_repository write_repository.

  3. Test

    The console checks that the forge answers and that the client ID and secret are accepted.

  4. Enable

    The forge appears in the users’ Settings → Git connections.

Deleting a forge revokes the connections that depend on it. Personal access tokens are disabled by default (Allow personal access tokens setting).

On the user side

  • Connect via …: authorization on the forge (PKCE, single-use state), automatic return.
  • Expiring tokens (GitLab: 2 h) are renewed automatically; a connection expired on the forge side shows Reconnect.
  • The repositories available through your connections then appear under the input box of a new conversation.

What Pi does on its own

In the sandbox, git, gh and glab are authenticated with a run token. The gateway intercepts the traffic to the forges and replaces it with the user’s OAuth token: Pi acts on their behalf, on all their repositories, without ever seeing the token.

  • push work branches (including force pushes) and tags;
  • open and update PRs/MRs, comment, answer reviews;
  • read the CI and job logs, re-run a pipeline;
  • read and create issues, releases.

Following the work: Git tab

  • Working branch: the conversation panel (Git tab) shows the current branch and lets you switch it, among the local branches and those of origin. It follows the branch switches made by Pi; a switch of yours is noted in the conversation and reported to Pi. Not possible while Pi is working.
  • git diff: the files changed since the last commit, with their differences file by file.
  • Co-author: every commit made in a sandbox carries the Co-Authored-By: Shipcove <address> trailer (address set in Git settings). It is added by platform Git hooks, which then run the repository’s own hooks (pre-commit, commitlint…).

What requires approval

OperationHow
Push to the default branch or a protected branchplatform_git_push tool
Merging a PR/MRplatform_merge_pull_request tool
Deleting a branchplatform_delete_remote_branch tool
Settings, access, protections, repository deletionReserved to a human, on the forge
SSH keys, deploy keys and tokens, tokens, runners, CI secretsForbidden from a sandbox

Refusals are explicit: git push shows ! [remote rejected] main -> main (…); gh and glab get an HTTP 403 with the reason. The approval request appears in the conversation, under Pi’s message: commits, diff, then Approve or Reject. It covers the exact operation (pinned commit), can be used only once and expires after 24 h. Every write and every refusal is audited.

The clone URL returned by the forge must point to the same host as the connection: a token is never presented to another host.

Internal forges over HTTP

HTTPS is required. An internal forge over HTTP (staging) is only reachable if the administrator lists host[:port] in Git forges → Git settings. Tokens then travel in clear text on that network: reserve this for trusted networks.
