Architecture

Stateless NestJS services coordinated by PostgreSQL, ephemeral sandboxes whose state lives on S3, and a gateway through which everything leaving a sandbox goes.

Browser ── nginx (web) ──► NestJS API (×N) ──► PostgreSQL (state, job queues, LISTEN/NOTIFY)
                                │                Vault (secrets)   Garage/S3 (checkpoints, attachments)
                                ▼
                           NestJS worker ──► Docker sandboxes (the agent in RPC mode, isolated internal network)
                                │                    │  support services (sandbox localhost)
                                ▼                    ▼
                      Gateway (LLM proxy, filtered egress, Git reads) ──► LiteLLM ──► providers
                      Preview gateway (separate domain) ──► sandbox ports

Components

ComponentRole
webAngular 22 (signals, zoneless) and Tailwind 4, served by nginx with a strict CSP; nginx balances across the API instances, resolving DNS on each request.
apiREST /api/v1 (OpenAPI), sessions, SSO, administration, SSE stream. Stateless: several instances.
workerRuns the runs (jobs taken from the database with SKIP LOCKED), drives the sandboxes, checkpoints, Git broker, purges and maintenance.
gatewayThe only way out of the sandboxes: LLM proxy (credit reservation and billing), allowlisted HTTP(S) proxy, forge proxy (intercepted TLS, OAuth token substituted, safeguards), Git reads with a run token.
previewExposes the sandbox ports on a separate domain, after a token exchange.
docker-guardSole holder of the Docker socket: only accepts from the worker the creation and driving of compliant sandboxes and services.
edge (optional)Caddy: automatic TLS for the application and the previews.

VaultSecrets (KV), one AppRole identity and one policy per service.
Garage (S3)Conversation checkpoints (sandbox files), attachments, the agent's state.
LiteLLMUnified access to model providers.

Run lifecycle

  1. Message

    The API stores the message and creates a job (or queues it if a run is in progress).

  2. Sandbox

    The worker takes the job, creates or wakes up the sandbox, restores the last checkpoint from S3, writes the agent's configuration (skills, MCP, service catalog) and runs the startup script if needed.

  3. The agent

    The agent (built on the open-source Pi engine) runs in RPC mode. The platform-bridge extension provides the platform tools (approved Git operations, support services, downloadable files, MCP); plugins add questions to the user (ask_user), screenshots (browser_screenshot) and the task plan (update_plan). Its LLM calls go through the gateway with a run token.

  4. Stream

    Events (text, tools, files) are masked, persisted and streamed over SSE to every API instance via NOTIFY.

  5. Checkpoint

    At the end of the run, the worker pushes an incremental checkpoint to S3. The sandbox stops after the idle timeout; it can be recreated anywhere from the checkpoint.

Key points

  • Recovery: if a worker disappears, its lock expires and another one resumes the run from the last known state.
  • Quotas: every LLM call reserves its maximum cost in a transaction before being forwarded; the actual cost is billed on the response. No overrun possible, even in parallel.
  • Git: git, gh and glab go through the gateway, which substitutes the OAuth token for the run token and applies the safeguards; sensitive operations (default branch, merge, deletion) go through the worker’s broker, after approval of a pinned operation.
  • Network: sandboxes are on an internal network without a route; their support services share their network namespace.
