Admin console

Reserved for platform administrators (MFA required). Every change is audited; most settings apply immediately to all instances.

Roles

RoleScope
Platform administratorAdmin console, catalogs, models, quotas, retention. Has no access to the content of private conversations, nor to the list of repositories users work on.
UserTheir conversations (with or without a repository), their Git connections, their personal skills and MCP servers, read-only sharing of their conversations.

Sections

Overview

Users, repositories, conversations and active sandboxes, LLM calls and credits consumed over 24 h, errors, health of the dependencies.

Users and invitations

Creation, suspension, deletion (anonymization), MFA reset, session revocation. Invitations send a sign-up link valid for 7 days, even when open sign-up is disabled.

IAM & sign-in

Local sign-in, sign-ups, email verification, MFA policy, session duration, lockout after failures, identity providers. See Identity and SSO.

Git forges

GitHub / GitLab OAuth applications that let users connect their accounts. Git settings: personal access tokens (disabled by default), internal forges reachable over HTTP, and the address of the Co-Authored-By: Shipcove trailer added to every commit (empty: no trailer). See Git forges.

Models (LiteLLM)

Connection: LiteLLM URL and admin key, stored in Vault (infra/litellm) and picked up by every service within 30 s; an existing LiteLLM proxy can thus replace the platform’s. Without a setting, the LITELLM_URL deployment value applies. The connection, the models (created, enabled, default) and the other settings of this console can also be declared by environment variables applied at every start: see Installation.

Discovery: the models declared in LiteLLM are read through its API (/model/info, otherwise /v1/models) when clicking Reload models, when the connection is saved and every 10 minutes. A new model arrives disabled, with capabilities and coefficients prefilled from LiteLLM (1 credit = $0.001); a model gone from LiteLLM is flagged missing and no longer offered.

Per-model settings: activation, default model (a single one, necessarily enabled), user allowlist (empty = available to everyone; applied to the model list, to conversation creation, to the sandbox and to the LLM gateway), display name, context window, capabilities and coefficients (credits per 1,000 input, output and cache tokens). Coefficients are versioned: a change does not affect past billing. The Test button sends a real request. The title model (optional) names conversations automatically; these short calls are not counted against quotas. The title is requested as constrained output (JSON Schema, adjustable maximum length, 60 characters by default), without a token limit: a model that reasons before answering gets all the way to the title. A provider without structured output gets the same instruction as free text; the length is always enforced.

Quotas & credits

Personal quotas in credits over 5 h and 7 days: a default limit for everyone, or one specific to a user (each person has a single counter, for all their conversations); exemptions and manual adjustments, ledger history. Every LLM call reserves an estimated cost before being forwarded (output capped by “Output tokens reserved per call”) and only bills the actual cost. A call is accepted as long as the window is not used up (consumed + in-flight reservations below the limit): the last call may therefore go slightly over, by its actual cost, then the agent is paused until quota frees up. Users only see percentages.

Sandboxes & previews

  • Resources per sandbox (CPU, memory, disk, processes), idle timeout, maximum run duration, number of active sandboxes per user and in total;
  • allowed outbound domains (package registries…), checkpoint exclusions (regenerable dependencies and caches — node_modules, .venv, __pycache__… — are excluded by default and reinstalled in every new sandbox; extra patterns possible);
  • startup script: a single bash script run in every new sandbox (npm / pip registries, mirrors, common tools) and its maximum duration — see Environment and services;
  • sandbox images: addition (reference + digest), activation as default image, deprecation;
  • services started by the agent: see Environment and services;
  • agent sub-agents: platform-wide switch, maximum number of sub-agents per call (4 by default, up to 8), number of explore sub-agents running at the same time (4 by default) and maximum duration of a sub-agent (20 min by default). Each sub-agent spends tokens from the user's quotas and runs a process in the sandbox: lower the parallelism for small sandboxes. Settings apply from the next run; a sandbox image without the plugin offers none — see Sub-agents;
  • previews: number of simultaneous ports per conversation;
  • running instances, with forced stop.

Skills & MCP

Skills (instructions for the agent) and MCP servers in two scopes — global (administrator) and personal — with per-tool permissions and allowed remote MCP hosts. A skill is available as soon as it is created; for a global skill, the administrator sets “enabled by default for everyone”, each user keeping control of their own switch. Skills can be deleted (by their author, or by an administrator for a global skill); if review of personal skills is required, they wait for an administrator’s approval. A skill only contains markdown files, possibly in folders; it is imported and exported as a .zip (see the guide). Skill categories are created, renamed, ordered and deleted here (their skills then become “uncategorized”); they organize the Skills page of all users. The automatic analysis flags in particular probable secrets, dangerous commands cited and prompt-injection phrasing. MCP server secrets are in Vault. A revocation applies from the next run.

Secrets & storage

Status of Vault and of the infrastructure secrets (never displaying a value), status of S3 storage.

Notifications & SMTP

SMTP server (password in Vault, test email), default notification policies.

Audit & retention

Search and CSV export of the audit log; retention periods per data type (events, tool outputs, attachments, checkpoints, notifications, audit, archived workspaces…), legal hold per type, purge history and Run purge now (otherwise automatic every hour). The current checkpoint generation is never purged: a kept conversation can always resume.
