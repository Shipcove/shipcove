Installation

Reference deployment on a Docker host, from the images published on ghcr.io/shipcove. For a first try, follow the quick start first.

Prerequisites

  • Linux x86_64, Docker 24+ with Compose v2, openssl, git;
  • at least 4 cores, 8 GB of RAM and 30 GB of disk, plus the resources of the sandboxes (2 GB and 1 CPU each by default);
  • two DNS names: the application (e.g. code.example.com) and a wildcard domain for previews (e.g. *.preview.example.com).

Images

ghcr.io/shipcove/shipcove-gatewayLLM proxy and quotas, filtered egress, Git reads

ghcr.io/shipcove/shipcove-docker-guardDocker engine guard (sole holder of the socket)
ghcr.io/shipcove/shipcove-sandboxSandbox image (the agent, Git, Python, Node.js)

Images are published with every version tag of the repository: vX.Y.Z gives the X.Y.Z, X.Y and latest tags (a pre-release vX.Y.Z-rc.N only publishes its own). All the images of an installation have the same version: pin it, do not deploy latest in production.

Configuration (.env)

git clone https://github.com/Shipcove/shipcove.git
cd shipcove/infrastructure/docker
cp .env.example .env
VariableDescription
CAP_REGISTRYghcr.io/shipcove/ (with the trailing slash). Empty = locally built images.
CAP_VERSIONVersion of the platform images.
CAP_SANDBOX_IMAGEDefault sandbox image, e.g. ghcr.io/shipcove/shipcove-sandbox:0.1.0.
CAP_PUBLIC_URLPublic URL, e.g. https://code.example.com (email links, SSO and OAuth callback URLs).
CAP_PREVIEW_DOMAIN, CAP_PREVIEW_SCHEME, CAP_PREVIEW_PORTPreview domain, e.g. preview.example.com, https, 443.
CAP_COOKIE_SECUREtrue behind HTTPS (required in production).
CAP_HTTP_BIND, CAP_HTTP_PORT, CAP_PREVIEW_BINDListening interfaces and port; 127.0.0.1 by default, behind the reverse proxy.
CAP_DOCKER_GIDGroup of the Docker socket: stat -c %g /var/run/docker.sock.
CAP_API_REPLICASNumber of API instances (2 by default).
CAP_ADMIN_EMAIL, CAP_ADMIN_PASSWORDInitial administrator, created only if no administrator exists.

The .env file contains no infrastructure secret. ./scripts/init-secrets.sh generates the bootstrap secrets in .secrets/ (never committed, to be backed up); the rest is created in Vault on first start. If you add the optional variables below with secrets in them, restrict the file (chmod 600 .env) or use the _FILE variants.

Configuration by environment variables (optional)

Instead of the administration console, the API can apply a configuration declared in .env at every start, so that a new instance is usable without any manual step. Every variable is optional; what is not declared stays managed in the console. What is declared is applied again at the next restart, and nothing is rewritten when the value is already in place. Secrets go to Vault, and each variable also accepts <NAME>_FILE (path of a mounted file).

LITELLM_SYNC_ON_START, LITELLM_SYNC_INTERVAL_MINUTESModel discovery at startup (on by default) and periodically.
LITELLM_ENABLED_MODELS, LITELLM_DEFAULT_MODEL, LITELLM_TITLE_MODELModels enabled (* for all), default model, model for conversation titles.
SSO_OIDC_*, SSO_SAML_*, SSO_LDAP_*, SSO_GITHUB_*, SSO_GITLAB_*, SSO_PROVIDERSIdentity providers: one per type with flat variables, or several in JSON.
GIT_GITLAB_*, GIT_GITHUB_*, GIT_FORGESGit forges (OAuth application: host, client ID, secret), and GIT_ALLOW_PERSONAL_TOKENS, GIT_INSECURE_HTTP_HOSTS, GIT_CO_AUTHOR_EMAIL.

Full reference with every variable and its default: docs/operations/environment.md; commented template at the end of .env.example. With Helm, use api.extraEnv or api.envFrom (a whole Secret).

Vault in production

Choose the unseal mode before the first start (CAP_VAULT_UNSEAL_MODE):

  • auto: a key service (AWS KMS, Google Cloud KMS, Azure Key Vault, transit of a corporate Vault) unseals Vault; stanza in vault/seal.hcl (template seal.hcl.example), optional credentials in vault/seal.env;
  • manual: keys are split between operators and encrypted for their PGP keys (.secrets/vault-pgp/*.asc); scripts/vault-unseal.sh after each Vault restart;
  • file (default): keys on disk, reserved for development and staging.

Starting

./scripts/init-secrets.sh
docker compose pull
docker pull ghcr.io/shipcove/shipcove-sandbox:0.1.0
docker compose up -d
docker compose ps

Compose handles the order: PostgreSQL, Vault (initialized and unsealed), Garage, bootstrap (Vault policies, buckets), migrations, then the application services. The dev profile (--profile dev) adds Mailpit and a mock LLM: do not enable it in production.

Built-in TLS (recommended)

The tls profile adds Caddy on ports 80 and 443, with automatic Let’s Encrypt certificates for the application and the previews:

CAP_DOMAIN=code.example.com
CAP_PREVIEW_DOMAIN=preview.example.com   # DNS: *.preview.example.com → the host
CAP_TLS_EMAIL=admin@example.com
CAP_PUBLIC_URL=https://code.example.com
CAP_PREVIEW_SCHEME=https
CAP_PREVIEW_PORT=443
CAP_COOKIE_SECURE=true
docker compose --profile tls up -d

Preview certificates are issued on demand, only for an open preview. If there are many previews (Let’s Encrypt rate limits), provide a wildcard certificate: CAP_TLS_PREVIEW=files and edge/certs/preview.crt / preview.key.

Your own reverse proxy

Otherwise, put a TLS reverse proxy (Caddy, Traefik, nginx…) in front of the two ports: the application on CAP_HTTP_PORT (8080) and the previews on CAP_PREVIEW_PORT (8090). It must forward the Host and X-Forwarded-* headers and must not buffer SSE streams.

code.example.com {
  reverse_proxy 127.0.0.1:8080 {
    flush_interval -1
  }
}
*.preview.example.com {
  tls { dns <provider> }
  reverse_proxy 127.0.0.1:8090
}

Previews must stay on a separate domain from the application (not a subdomain that would share its cookies): the code a preview runs is not trusted.

Emails

Configure the SMTP server in Administration → Notifications & SMTP (password stored in Vault), or with the SMTP_* variables, and send a test email. Without SMTP, invitations and password resets are not sent.

Upgrading

  1. Read the release notes; back up PostgreSQL, Vault and .secrets/ (see Operations).
  2. Change CAP_VERSION and CAP_SANDBOX_IMAGE in .env.
  3. docker compose pull && docker pull <new sandbox image>
  4. docker compose up -d: migrations are applied before the API and the worker restart.

Running runs resume after the worker restarts (database locks, S3 checkpoints). Existing sandboxes keep their image until they are next created.
