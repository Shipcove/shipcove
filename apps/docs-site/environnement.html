Environnement et services

Ce dont l’agent a besoin pour installer, lancer et tester le code de vos dépôts : variables, secrets, préparation, image et services d’appui.

Variables et secrets

Par dépôt Git, dans Administration → Dépôts & environnements (administrateur plateforme). Elles s’appliquent à toutes les conversations sur ce dépôt, quel que soit l’utilisateur, à partir du run suivant. Une conversation sans dépôt n’a pas de variables d’environnement.

  • Injectées dans l’environnement de l’agent (et de ses commandes), jamais écrites sur disque par la plateforme : elles n’entrent pas dans les checkpoints.
  • Secrets : stockés dans Vault, jamais réaffichés (6 caractères minimum). Ils sont masqués (***) dans les sorties d’outils, les réponses de l’agent (même coupés entre deux fragments du flux), le flux temps réel, la base de données, et retirés des requêtes envoyées au fournisseur LLM.
  • Noms réservés refusés : PATH, HOME, *_PROXY, LD_*, CAP_*, PI_*, GH_*, GITHUB_TOKEN, GITLAB_TOKEN, certificats, GIT_SSH*…

Comme pour les secrets de CI, l’agent de toute conversation sur le dépôt peut utiliser un secret (et donc l’écrire dans un fichier ou l’envoyer vers un hôte autorisé). Réservez-y des identifiants de développement à droits minimaux.

Outils globaux

L’agent tourne sans droits root : npm install -g (Angular CLI, pnpm…) installe dans son répertoire (~/.local, déjà dans le PATH). Ces outils vivent avec la sandbox ; pour les retrouver dans chaque nouvelle sandbox, ajoutez-les au script de préparation.

Script de préparation

Script bash exécuté dans /workspace avec les variables du dépôt, dans chaque nouvelle sandbox et à chaque modification du script ou de l’image. Il doit être idempotent, comme une étape de CI :

npm ci
pip install -r requirements.txt
  • Ce qu’il produit dans /workspace est conservé (checkpoint) ; le reste vit avec la sandbox.
  • Sa sortie (secrets masqués) apparaît dans la conversation ; en cas d’échec, l’agent est informé et le run continue.
  • Durée maximale : 20 minutes par défaut.

Image de sandbox

Chaque dépôt peut utiliser une des images actives déclarées par l’administrateur (ex. une variante avec un JDK, Go ou Rust). L’image officielle ghcr.io/shipcove/shipcove-sandbox contient Pi (et son plugin de captures d’écran), Git, Python, uv, Node.js, npm, Playwright et Chromium ; une image dérivée part de celle-ci (FROM ghcr.io/shipcove/shipcove-sandbox:<version>@sha256:…). Changer d’image recrée la sandbox au run suivant.

Services lancés par l’agent

Pi démarre lui-même, quand il en a besoin, des bases de données, caches ou files de messages choisis dans un catalogue géré par l’administrateur (Administration → Sandboxes & previews) : image, port, sonde de santé, variables par défaut, mémoire. Rien ne démarre tant que l’agent ne le demande pas ; aucun réglage côté utilisateur.

  • L’agent utilise l’outil platform_services : start, stop, status, logs, catalog. Dans les variables d’un service, ${NOM} reprend une variable ou un secret du dépôt sans que l’agent en connaisse la valeur (ex. POSTGRES_PASSWORD=${DB_PASSWORD}).
  • Chaque service partage le réseau de sa sandbox : joignable sur localhost depuis celle-ci uniquement, sans plus d’accès sortant qu’elle. Conteneurs durcis et limités (mémoire, CPU, processus), 4 services au plus par sandbox par défaut.
  • Les services durent autant que la sandbox et disparaissent avec elle : données éphémères, l’agent refait migrations et données de test après un redémarrage.

Miroir de registre

Sans accès direct aux registres publics, Administration → Sandboxes & previews → Miroir de registre fait télécharger les images des services depuis votre miroir (Harbor, Nexus, Artifactory…) : chaque registre d’origine est associé à un préfixe du miroir (docker.io → harbor.corp/dockerhub donne harbor.corp/dockerhub/library/redis:7.4-alpine), avec des identifiants facultatifs stockés dans Vault et un repli possible sur le registre d’origine. Le téléchargement est fait par le moteur Docker de l’hôte : un miroir en HTTP ou à certificat interne doit y être déclaré.

Les services d’appui sont disponibles avec le provider Docker ; ils le seront sur Kubernetes (conteneurs annexes du Pod) avec la validation du chart Helm.
