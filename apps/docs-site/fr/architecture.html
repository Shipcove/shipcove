Architecture

Des services NestJS sans état coordonnés par PostgreSQL, des sandboxes éphémères dont l’état vit sur S3, et une passerelle par laquelle passe tout ce qui sort d’une sandbox.

Navigateur ── nginx (web) ──► API NestJS (×N) ──► PostgreSQL (état, files de jobs, LISTEN/NOTIFY)
                                   │                Vault (secrets)   Garage/S3 (checkpoints, pièces jointes)
                                   ▼
                              Worker NestJS ──► sandboxes Docker (Pi en RPC, réseau interne isolé)
                                   │                     │  services d'appui (localhost de la sandbox)
                                   ▼                     ▼
                         Gateway (proxy LLM, egress filtré, lecture Git) ──► LiteLLM ──► fournisseurs
                         Preview gateway (domaine distinct) ──► ports des sandboxes

Composants

ComposantRôle
webAngular 22 (signals, zoneless) et Tailwind 4, servi par nginx avec une CSP stricte ; nginx répartit vers les instances de l’API en résolvant le DNS à chaque requête.
apiREST /api/v1 (OpenAPI), sessions, SSO, administration, flux SSE. Sans état : plusieurs instances.
workerExécute les runs (jobs pris en base avec SKIP LOCKED), pilote les sandboxes, checkpoints, broker Git, purges et maintenance.
gatewaySeule sortie des sandboxes : proxy LLM (réservation et facturation des crédits), proxy HTTP(S) à liste blanche, proxy des forges (TLS intercepté, jeton OAuth substitué, garde-fous), lecture Git avec jeton de run.
previewExpose les ports des sandboxes sur un domaine distinct, après échange d’un jeton.
docker-guardSeul détenteur du socket Docker : n’accepte du worker que la création et la conduite de sandboxes et services conformes.
edge (optionnel)Caddy : TLS automatique pour l’application et les previews.
PostgreSQL 18Source de vérité, files de jobs, verrous, notifications temps réel (LISTEN/NOTIFY).
VaultSecrets (KV), une identité AppRole et une politique par service.
Garage (S3)Checkpoints des conversations (fichiers des sandboxes), pièces jointes, état de Pi.
LiteLLMAccès unifié aux fournisseurs de modèles.

Cycle de vie d’un run

  1. Message

    L’API enregistre le message et crée un job (ou le met en file si un run est en cours).

  2. Sandbox

    Le worker prend le job, crée ou réveille la sandbox, restaure le dernier checkpoint depuis S3, écrit la configuration de Pi (skills, MCP, catalogue des services) et lance le script de démarrage si nécessaire.

  3. Pi

    Pi tourne en mode RPC. L’extension platform-bridge lui fournit les outils de la plateforme (opérations Git approuvées, services d’appui, fichiers à télécharger, MCP) ; des plugins ajoutent les questions à l’utilisateur (ask_user), les captures d’écran (browser_screenshot) et le plan de tâches (update_plan). Ses appels LLM passent par la gateway avec un jeton de run.

  4. Flux

    Les événements (texte, outils, fichiers) sont masqués, persistés et diffusés en SSE à toutes les instances de l’API via NOTIFY.

  5. Checkpoint

    En fin de run, le worker pousse un checkpoint incrémental vers S3. La sandbox s’arrête après le délai d’inactivité ; elle peut être recréée n’importe où à partir du checkpoint.

Points clés

  • Reprise : si un worker disparaît, son verrou expire et un autre reprend le run depuis le dernier état connu.
  • Quotas : chaque appel LLM réserve son coût maximal en transaction avant d’être transmis ; le coût réel est facturé à la réponse. Aucun dépassement possible, même en parallèle.
  • Git : git, gh et glab passent par la gateway, qui substitue le jeton OAuth au jeton de run et applique les garde-fous ; les opérations sensibles (branche par défaut, fusion, suppression) passent par le broker du worker, après approbation d’une opération figée.
  • Réseau : les sandboxes sont sur un réseau interne sans route ; leurs services d’appui partagent leur espace réseau.
