Sécurité

Principe : le code exécuté par l’agent n’est pas de confiance. La sandbox ne détient aucun secret permanent ; elle agit sur les forges au nom de l’utilisateur, mais ce qui est irréversible ou durable exige une approbation humaine.

Sandboxes

  • Utilisateur non privilégié, cap-drop ALL, no-new-privileges, limites de CPU, mémoire, processus et disque.
  • Réseau interne sans route vers Internet ni vers le backend (PostgreSQL, Vault, S3…).
  • Sortie uniquement via le proxy de la gateway, avec une liste blanche de domaines (registres de paquets…). Le trafic vers les forges Git est intercepté (voir ci-dessous).
  • Services d’appui : mêmes durcissements, aucun accès réseau supplémentaire.

Jetons et secrets

  • La sandbox reçoit un jeton de run à durée limitée, utilisable seulement auprès de la gateway (LLM, lecture Git, outils de la plateforme).
  • Clés de modèles, jetons Git, secrets SSO et MCP sont dans Vault ; l’API ne les renvoie jamais.
  • Les valeurs secrètes injectées dans l’agent sont masquées dans les sorties, le flux temps réel, la base, et retirées des requêtes vers le fournisseur LLM.
  • Chaque service a sa propre identité Vault et une politique limitée à ses chemins.

Git

  • git, gh et glab fonctionnent dans la sandbox avec le jeton de run. La gateway termine le TLS des seules forges avec une autorité propre à l’installation (clé privée dans Vault), puis remplace ce jeton par le jeton OAuth de l’utilisateur. Le jeton de la forge n’entre jamais dans la sandbox.
  • Garde-fous appliqués par la gateway, quel que soit l’outil : pas de push sur la branche par défaut ni sur une branche protégée, pas de fusion, de suppression de branche ou de tag, de modification des réglages ou des accès du dépôt, ni de création de clé, de jeton, de runner ou de secret de CI.
  • Ces opérations passent par le broker, après approbation de l’opération exacte (commit figé, branche, cible), dans la conversation ; une approbation est à usage unique et invalidée si la branche a bougé.
  • Chaque écriture de l’agent sur une forge, et chaque refus, est audité (git.agent_write).
  • Un jeton n’est présenté qu’à l’hôte de sa connexion ; HTTPS est obligatoire sauf exception explicite de l’administrateur.

Comptes et navigateur

  • Mots de passe Argon2id, MFA TOTP (obligatoire pour les administrateurs), verrouillage et limitation de débit.
  • Sessions côté serveur, cookies HttpOnly / SameSite, protection CSRF par double soumission.
  • CSP stricte sans script inline, en-têtes de sécurité, previews sur un domaine distinct avec jeton.
  • SSO : PKCE, état à usage unique, assertions SAML signées ; jamais de fusion de comptes par email.

Fichiers

Pièces jointes et archives contrôlées (type réel, taille décompressée, nombre d’entrées, chemins), analyse antivirus par ClamAV si CLAMAV_HOST est configuré, bloquante en cas d’indisponibilité, exécutables refusés. Les fichiers que Pi propose au téléchargement sont toujours servis en pièce jointe, jamais interprétés par le navigateur.

Confidentialité

Une conversation n’est lisible que par son propriétaire et les personnes avec qui il l’a partagée nommément — les administrateurs plateforme compris. Les actions d’administration sont auditées ; la rétention est configurable avec gel légal.

Hôte et infrastructure

  • Garde Docker : seul le service docker-guard accède au socket Docker. Le worker l’appelle sur un réseau interne dédié, avec un secret partagé ; le garde n’accepte que des sandboxes et services conformes (non privilégiés, sans capacité ajoutée, sans montage de l’hôte, limites obligatoires) et seulement sur les conteneurs de la plateforme. Un worker compromis ne peut donc pas prendre la main sur l’hôte.
  • gVisor (optionnel) : CAP_SANDBOX_RUNTIMES=runsc pour isoler en plus les sandboxes du noyau de l’hôte.
  • Vault : en production, déverrouillage par un service de clés (auto) ou par des clés réparties entre opérateurs, chiffrées pour leurs clés PGP (manual) ; le jeton root est révoqué après l’amorçage. Voir Exploitation.
  • TLS : point d’entrée Caddy intégré (profil tls), certificats automatiques ; un certificat de preview n’est émis que pour une preview ouverte.

Points d’attention en production

  • Mode de Vault : le mode par défaut (file) garde clés et jeton root sur disque ; choisissez manual ou auto avant la première installation.
  • Garde Docker : il reste un composant de confiance (accès root effectif) ; dédiez l’hôte à la plateforme.
  • Trafic interne : les liaisons entre services Compose ne sont pas chiffrées (même hôte) ; à chiffrer pour un déploiement multi-hôte.
  • Script de démarrage : stocké en clair et exécuté dans chaque sandbox, où l’agent peut lire ce qu’il écrit (~/.npmrc…) ; n’y mettez que des identifiants en lecture seule.
  • Forges : pendant un run, l’agent agit sur tous les dépôts accessibles à l’utilisateur (pousser des branches, ouvrir des PR, commenter). Une injection de prompt peut l’y pousser ; elle ne peut ni fusionner, ni toucher la branche par défaut, ni emporter le jeton.

Pour signaler une vulnérabilité, ouvrez un avis de sécurité privé sur le dépôt GitHub plutôt qu’un ticket public.
