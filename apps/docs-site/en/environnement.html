Environment and services

What the agent needs to install, run and test the code: sandbox startup script, image and support services.

Startup script

A single script, defined by the administrator in Administration → Sandboxes & previews → Startup script, shared by all sandboxes (with or without a repository). It is the place to configure the company’s registries and mirrors and install common tools:

npm config set registry https://npm.example.corp/
pip config set global.index-url https://pypi.example.corp/simple
npm install -g pnpm@10
  • Run with bash in /workspace, without root privileges, in every new sandbox before the first message handled by Pi, and again when it changes: it must be idempotent.
  • What it produces in /workspace is kept (checkpoint); the rest (~/.npmrc, pip configuration, global tools in ~/.local) lives with the sandbox and is redone in the next one.
  • Its output appears in the conversation; if it fails, the agent is told and the run continues. Maximum duration: 20 minutes by default.
  • The hosts it contacts must be in the allowed outbound network (same page).
  • uv does not read the pip configuration: for a private index, also write ~/.config/uv/uv.toml ([[index]] with default = true).

The script is stored in clear text and runs in the sandbox, where the agent can read the files it writes: only put read-only credentials with minimal scope in it.

Sandbox image

All sandboxes use the default image declared by the administrator. The official image ghcr.io/shipcove/shipcove-sandbox contains Pi (and its plugins: questions, screenshots, plan), Git, Python, uv, Node.js, npm, Playwright and Chromium; a derived image starts from it (FROM ghcr.io/shipcove/shipcove-sandbox:<version>@sha256:…), for example to add a JDK, Go or Rust. Changing the default image recreates the sandboxes at the next run.

Services started by the agent

Pi starts by itself, when it needs them, databases, caches or message queues chosen from a catalog managed by the administrator (Administration → Sandboxes & previews): image, port, health probe, default variables, memory. Nothing starts until the agent asks for it; no setting on the user side.

  • The agent uses the platform_services tool: start, stop, status, logs, catalog.
  • Each service shares the network of its sandbox: reachable on localhost from it only, with no more outbound access than it has. Hardened and limited containers (memory, CPU, processes), at most 4 services per sandbox by default.
  • Services live as long as the sandbox and disappear with it: ephemeral data, the agent redoes migrations and test data after a restart.

Registry mirror

Without direct access to public registries, Administration → Sandboxes & previews → Registry mirror makes the service images download from your mirror (Harbor, Nexus, Artifactory…): each source registry is mapped to a mirror prefix (docker.io → harbor.corp/dockerhub gives harbor.corp/dockerhub/library/redis:7.4-alpine), with optional credentials stored in Vault and an optional fallback to the source registry. The download is done by the host’s Docker engine: a mirror over HTTP or with an internal certificate must be declared there.

Support services are available with the Docker provider; they will be on Kubernetes (Pod sidecar containers) once the Helm chart is validated.
