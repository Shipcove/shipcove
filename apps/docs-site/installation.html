Installation

Déploiement de référence sur un hôte Docker, à partir des images publiées sur ghcr.io/shipcove. Pour un premier essai, suivez d’abord le démarrage rapide.

Prérequis

  • Linux x86_64, Docker 24+ avec Compose v2, openssl, git ;
  • 4 cœurs, 8 Go de RAM et 30 Go de disque au minimum, plus les ressources des sandboxes (2 Go et 1 CPU chacune par défaut) ;
  • deux noms DNS : l’application (ex. code.exemple.com) et un domaine générique pour les previews (ex. *.preview.exemple.com).

Images

ImageRôle
ghcr.io/shipcove/shipcove-webInterface Angular et nginx (point d’entrée HTTP)
ghcr.io/shipcove/shipcove-apiAPI REST, authentification, flux temps réel (aussi utilisée pour les migrations)
ghcr.io/shipcove/shipcove-workerOrchestration des runs, sandboxes, checkpoints, broker Git
ghcr.io/shipcove/shipcove-gatewayProxy LLM et quotas, egress filtré, lecture Git
ghcr.io/shipcove/shipcove-previewAccès aux previews
ghcr.io/shipcove/shipcove-docker-guardGarde du moteur Docker (seul détenteur du socket)
ghcr.io/shipcove/shipcove-sandboxImage de sandbox (Pi, Git, Python, Node.js)

Toutes les images portent la même version (0.1.0…). Épinglez-la ; ne déployez pas latest en production.

Configuration (.env)

git clone https://github.com/Shipcove/shipcove.git
cd shipcove/infrastructure/docker
cp .env.example .env
VariableDescription
CAP_REGISTRYghcr.io/shipcove/ (avec la barre finale). Vide = images construites localement.
CAP_VERSIONVersion des images de la plateforme.
CAP_SANDBOX_IMAGEImage de sandbox par défaut, ex. ghcr.io/shipcove/shipcove-sandbox:0.1.0.
CAP_PUBLIC_URLURL publique, ex. https://code.exemple.com (liens des emails, URL de retour SSO et OAuth).
CAP_PREVIEW_DOMAIN, CAP_PREVIEW_SCHEME, CAP_PREVIEW_PORTDomaine des previews, ex. preview.exemple.com, https, 443.
CAP_COOKIE_SECUREtrue derrière HTTPS (obligatoire en production).
CAP_HTTP_BIND, CAP_HTTP_PORT, CAP_PREVIEW_BINDInterfaces et port d’écoute ; 127.0.0.1 par défaut, derrière le reverse proxy.
CAP_DOCKER_GIDGroupe du socket Docker : stat -c %g /var/run/docker.sock.
CAP_API_REPLICASNombre d’instances de l’API (2 par défaut).
CAP_ADMIN_EMAIL, CAP_ADMIN_PASSWORDAdministrateur initial, créé seulement si aucun administrateur n’existe.

Le fichier .env ne contient aucun secret d’infrastructure. ./scripts/init-secrets.sh génère les secrets d’amorçage dans .secrets/ (jamais versionné, à sauvegarder) ; le reste est créé dans Vault au premier démarrage.

Vault en production

Choisissez le mode de déverrouillage avant le premier démarrage (CAP_VAULT_UNSEAL_MODE) :

  • auto : un service de clés (AWS KMS, Google Cloud KMS, Azure Key Vault, transit d’un Vault d’entreprise) déverrouille Vault ; stanza dans vault/seal.hcl (modèle seal.hcl.example), identifiants éventuels dans vault/seal.env ;
  • manual : les clés sont réparties entre opérateurs et chiffrées pour leurs clés PGP (.secrets/vault-pgp/*.asc) ; scripts/vault-unseal.sh après chaque redémarrage de Vault ;
  • file (défaut) : clés sur disque, réservé au développement et à la recette.

Démarrage

./scripts/init-secrets.sh
docker compose pull
docker pull ghcr.io/shipcove/shipcove-sandbox:0.1.0
docker compose up -d
docker compose ps

L’ordre est géré par Compose : PostgreSQL, Vault (initialisé et déverrouillé), Garage, amorçage (politiques Vault, buckets), migrations, puis les services applicatifs. Le profil dev (--profile dev) ajoute Mailpit et un LLM factice : ne l’activez pas en production.

TLS intégré (recommandé)

Le profil tls ajoute Caddy sur les ports 80 et 443, avec des certificats Let’s Encrypt automatiques pour l’application et les previews :

CAP_DOMAIN=code.exemple.com
CAP_PREVIEW_DOMAIN=preview.exemple.com   # DNS : *.preview.exemple.com → l’hôte
CAP_TLS_EMAIL=admin@exemple.com
CAP_PUBLIC_URL=https://code.exemple.com
CAP_PREVIEW_SCHEME=https
CAP_PREVIEW_PORT=443
CAP_COOKIE_SECURE=true
docker compose --profile tls up -d

Les certificats de preview sont émis à la demande, uniquement pour une preview ouverte. Si les previews sont nombreuses (limites d’émission de Let’s Encrypt), fournissez un certificat wildcard : CAP_TLS_PREVIEW=files et edge/certs/preview.crt / preview.key.

Votre propre reverse proxy

Sinon, placez un reverse proxy TLS (Caddy, Traefik, nginx…) devant les deux ports : l’application sur CAP_HTTP_PORT (8080) et les previews sur CAP_PREVIEW_PORT (8090). Il doit transmettre les en-têtes Host et X-Forwarded-* et ne pas mettre en tampon les flux SSE.

code.exemple.com {
  reverse_proxy 127.0.0.1:8080 {
    flush_interval -1
  }
}
*.preview.exemple.com {
  tls { dns <fournisseur> }
  reverse_proxy 127.0.0.1:8090
}

Les previews doivent rester sur un domaine distinct de l’application (pas un sous-domaine qui partagerait ses cookies) : le code qu’exécute une preview n’est pas de confiance.

Emails

Configurez le serveur SMTP dans Administration → Notifications & SMTP (mot de passe stocké dans Vault) et envoyez un email de test. Sans SMTP, invitations et réinitialisations de mot de passe ne partent pas.

Mettre à jour

  1. Lisez les notes de version ; sauvegardez PostgreSQL, Vault et .secrets/ (voir Exploitation).
  2. Changez CAP_VERSION et CAP_SANDBOX_IMAGE dans .env.
  3. docker compose pull && docker pull <nouvelle image de sandbox>
  4. docker compose up -d : les migrations s’appliquent avant le redémarrage de l’API et du worker.

Les runs en cours sont repris après le redémarrage du worker (verrous en base, checkpoints S3). Les sandboxes existantes gardent leur image jusqu’à leur prochaine création.
