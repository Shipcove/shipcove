Security

Principle: the code run by the agent is not trusted. The sandbox holds no permanent secret; it acts on the forges on the user’s behalf, but anything irreversible or long-lived requires human approval.

Sandboxes

  • Unprivileged user, cap-drop ALL, no-new-privileges, CPU, memory, process and disk limits.
  • Internal network without a route to the Internet or to the backend (PostgreSQL, Vault, S3…).
  • Outbound traffic only through the gateway proxy, with an allowlist of domains (package registries…). Traffic to Git forges is intercepted (see below).
  • Support services: same hardening, no extra network access.

Tokens and secrets

  • The sandbox receives a time-limited run token, usable only with the gateway (LLM, Git reads, platform tools).
  • Model keys, Git tokens, SSO and MCP secrets are in Vault; the API never returns them.
  • Secret values injected into the agent are masked in outputs, the real-time stream and the database, and removed from requests to the LLM provider.
  • Each service has its own Vault identity and a policy limited to its paths.

Git

  • git, gh and glab work in the sandbox with the run token. The gateway terminates TLS for the forges only with an installation-specific authority (private key in Vault), then replaces that token with the user’s OAuth token. The forge token never enters the sandbox.
  • Safeguards enforced by the gateway, whatever the tool: no push to the default branch or to a protected branch, no merge, no branch or tag deletion, no change to the repository settings or access, and no creation of keys, tokens, runners or CI secrets.
  • These operations go through the broker, after approval of the exact operation (pinned commit, branch, target) in the conversation; an approval is single-use and invalidated if the branch has moved.
  • Every write by the agent on a forge, and every refusal, is audited (git.agent_write).
  • A token is only presented to the host of its connection; HTTPS is required unless the administrator makes an explicit exception.

Accounts and browser

  • Argon2id passwords, TOTP MFA (required for administrators), lockout and rate limiting.
  • Server-side sessions, HttpOnly / SameSite cookies, double-submit CSRF protection.
  • Strict CSP without inline scripts, security headers, previews on a separate domain with a token.
  • SSO: PKCE, single-use state, signed SAML assertions; accounts are never merged by email.

Files

Attachments and archives are checked (actual type, decompressed size, number of entries, paths), antivirus scanning with ClamAV if CLAMAV_HOST is configured, blocking when unavailable, executables refused. Files the agent offers as downloads are always served as attachments, never rendered by the browser.

Privacy

A conversation can only be read by its owner and the people they shared it with by name — platform administrators included. Administration actions are audited; retention is configurable with legal hold.

Host and infrastructure

  • Docker guard: only the docker-guard service accesses the Docker socket. The worker calls it on a dedicated internal network, with a shared secret; the guard only accepts compliant sandboxes and services (unprivileged, no added capability, no host mount, mandatory limits) and only on the platform’s containers. A compromised worker therefore cannot take over the host.
  • gVisor (optional): CAP_SANDBOX_RUNTIMES=runsc to further isolate the sandboxes from the host kernel.
  • Vault: in production, unsealing by a key service (auto) or by keys split between operators, encrypted for their PGP keys (manual); the root token is revoked after bootstrap. See Operations.
  • TLS: built-in Caddy entry point (tls profile), automatic certificates; a preview certificate is only issued for an open preview.

Points of attention in production

  • Vault mode: the default mode (file) keeps keys and root token on disk; choose manual or auto before the first installation.
  • Docker guard: it remains a trusted component (effective root access); dedicate the host to the platform.
  • Internal traffic: links between Compose services are not encrypted (same host); encrypt them for a multi-host deployment.
  • Startup script: stored in clear text and run in every sandbox, where the agent can read what it writes (~/.npmrc…); only put read-only credentials in it.
  • Forges: during a run, the agent acts on all the repositories available to the user (pushing branches, opening PRs, commenting). A prompt injection can push it to do so; it can neither merge, nor touch the default branch, nor take the token away.

To report a vulnerability, open a private security advisory on the GitHub repository rather than a public issue.
